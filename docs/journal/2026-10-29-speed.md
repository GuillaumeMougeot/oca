# Where the time goes (local CPU)

**Status:** RESOLVED. The model is the bottleneck, not Python, OpenCode or llama.cpp. The cluster and the GPU are the fixes.

## Question
The owner found the agent slow. Would vLLM, or Rust instead of Python, be faster?

## Measurements (llama-server log, Qwen3.6-35B-A3B Q4, CPU, 16 threads)
- **Cold start:** every OpenCode session opens with an 11.1k-token system prompt plus tool definitions. That costs about 100 s of prefill at 111 tok/s.
- **Warm start:** llama.cpp's RAM prompt cache (`--cache-ram`, default 8 GiB) restores that prefix, so each request then prefills in 0.3 to 3.8 s.
- **Bug-fix task:** 201 s cold, 70 s warm (three runs, all correct). The warm time is mostly generation at about 12 tok/s.
- **Cache misses:** the cache misses whenever the system prompt changes. That is what made my second run cold: I had just changed the permission rules. Any OpenCode config change makes the next session cold.

## Answer
- **oca's Python:** runs for about 0.3 s, then `exec`s OpenCode, so it costs nothing during a session. Rust would not change the speed.
- **OpenCode's TypeScript overhead:** negligible next to inference.
- **vLLM:** no gain on CPU. On GPUs it wins: FP8/FP4 kernels, batching and speculative decoding. That makes it the cluster engine.
- **Remaining CPU lever:** MTP speculative decoding (`--spec-type draft-mtp`). It needs an MTP GGUF and a single slot (`-np 1`), and is claimed to be 1.5 to 2 times faster. Untested.

## Dead ends
- **Disabling OpenCode's title agent:** meant to stop its concurrent request. Unnecessary once the prompt cache works, and its effect is unverified, so it was reverted.
- **Harness hangs:** two hangs were caused by my test harness, not by OpenCode.
  - `opencode run` reads stdin when stdin is a pipe, so scripts need `< /dev/null`.
  - `timeout` under `/usr/bin/time` puts OpenCode in a background process group, where touching the terminal stops it with SIGTTIN.
