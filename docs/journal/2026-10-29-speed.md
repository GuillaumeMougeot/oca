# Where the time goes (local CPU)

**Status:** RESOLVED. The model is the bottleneck, not Python. The bug-fix task went from 201 s to 38 s on CPU through prompt caching, MTP drafting, and no title generation.

## Question
The agent felt slow. Would vLLM, or Rust instead of Python, be faster?

## Measurements (llama-server log, Qwen3.6-35B-A3B Q4, CPU, 16 threads)
- **Cold start:** every OpenCode session opens with an 11.1k-token system prompt plus tool definitions. That costs about 100 s of prefill at 111 tok/s.
- **Warm start:** llama.cpp's RAM prompt cache (`--cache-ram`, default 8 GiB) restores that prefix, so each request then prefills in 0.3 to 3.8 s.
- **Cache misses:** any change to the system prompt (for example editing the permission rules) makes the next session cold.
- **Generation:** about 12 tok/s with a short context, but only 7.5 to 9.5 tok/s inside an agent turn with a 12k-token context.

## Speed-ups (bug-fix task, 3 runs each, all correct)

| Setup | Wall time |
|---|---|
| Cold, as first shipped | 201 s |
| Warm prompt cache | 70 s |
| + MTP, 3 draft tokens, `--parallel 1` | 67 to 124 s |
| + OpenCode title agent disabled | **38 s** |

### MTP (`--spec-type draft-mtp`)
Benchmark, short context, 600 tokens:

| Draft tokens | Generation |
|---|---|
| none | 11.9 tok/s |
| 2 | 16.7 tok/s |
| **3** | **20.5 tok/s** (84% accepted) |
| 4 | 17.5 tok/s |

In agent turns with a long context, MTP gives 13 to 15 tok/s against 7.5 to 9.5 without.

### Title agent
- MTP requires a single slot, so the first turn waits behind OpenCode's title request.
- Writing a title, the reasoning model thinks for 500 to 1,400 tokens: 29 to 84 s per session.
- Disabling the `title` agent removes that wait; sessions keep a default title.

## Answer
- **oca's Python:** runs for about 0.3 s, then `exec`s OpenCode, so it costs nothing during a session. Rust would not change the speed.
- **vLLM:** no gain on CPU. On GPUs it wins: FP8/FP4 kernels, batching and speculative decoding. That makes it the cluster engine.

## Pitfalls
Two hangs were caused by my test harness, not by OpenCode:
- `opencode run` reads stdin when stdin is a pipe, so scripts need `< /dev/null`.
- `timeout` under `/usr/bin/time` puts OpenCode in a background process group, where touching the terminal stops it with SIGTTIN.

The first title-disable test ran into this, so it looked broken until it was retried.

## Update (2026-10-30): titles come back on the cluster
With thinking off, a title is free on a UCloud server: the bug-fix task took 3.6 s with a title and 3.7 s without. On the local CPU server it is not: the title request evicts the session's cached prompt from the single slot, and the task took 77 to 121 s against 39 s. So titles are on only while a cluster server answers at launch.
