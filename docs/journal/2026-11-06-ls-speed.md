# Speed of `oca ls`

**Status:** OPEN. Two directions are done; sharing SSH connections waits for a measurement with spark2 on.

## Question
`oca ls` is slow, more so when a server does not answer; will more servers make it slower? (user, 2026-11-06)

## Measured (2026-11-06, spark2 off the VPN)
| Part | Time |
|---|---|
| `oca ls` in all | 10.1 s |
| this machine | 0.03 s |
| UCloud without a job (two API calls) | 0.24 s |
| spark2, unreachable: SSH's `ConnectTimeout=10` | 10.0 s |
| `oca serve --status` itself, run here | 0.09 s |

Servers were already asked in parallel, so `oca ls` takes as long as the slowest server; more servers do not add up. A machine over SSH that is off costs the SSH timeout. One that is on costs two SSH handshakes, to the VPS and through it to the Spark, plus 0.1 s of `oca serve`.

## Directions
| Direction | Verdict |
|---|---|
| Parallel checks | Already there |
| Shorter timeout | Done, for `oca ls` only: 3 s to connect, 10 s in all. Opening a model keeps 10 s, since a false "down" there opens a menu |
| Show at once, fill in | Done: in a terminal the ids show at once and each state as it arrives; in a pipe the list prints once, at the end |
| Reuse SSH connections (OpenSSH's ControlMaster, as Ansible does) | Next, if worth it: calls within a few minutes skip both handshakes, which also speeds opening a model on a Spark (two or three SSH calls). Cost: a connection that dies while kept makes calls wait for its keepalive, about 10 s |
| A daemon that polls servers | No: its states go stale (a "ready" that is not), it loads the Spark and the VPS, and it is one more process to manage. The router's own check, every 60 s, covers only servers it is connected to |

With spark2 off, `oca ls` now takes 3.1 s, and its list shows at once.

Expectation with spark2 on: `time ssh spark2 true` takes 0.5 to 1.5 s, and `oca ls` about as long. If the handshakes cost over 0.5 s, share connections.
