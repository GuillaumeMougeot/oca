# Security on a shared machine

**Status:** RESOLVED. Every server oca runs needs a key, and the files that hold keys are private.

## Finding (2026-10-30)
- This workstation has another user with running processes.
- Every port oca opens is on 127.0.0.1, which all users of a machine share: the router (8080), llama-server (8081), the web UI (4096) and the tunnel to the UCloud server (8001).
- A request to the UCloud server through the tunnel, with no credentials, returned 200. Another user could have run work on our GPU-hours, or started our local model.
- oca's config files were mode 644. The home directory happened to protect them.

## Design
- **Router and llama-server:** both take the user's key, `~/.config/oca/api-key`. OpenCode sends it through the provider's `apiKey`. llama-server reads it with `--api-key-file`, because an argument would show in `ps`.
- **UCloud servers:** each new job gets its own key, passed to vLLM with `--api-key`. `/health` and `/metrics` stay open, for the waits and the idle stop. The key is in the listing on the project drive, where members read it to join. The job's self-test sends it.
- **Files:** configs, state, listings and job scripts go through `write_private` (mode 600).
- **Web UI:** it already had its password.

## Check (a 1×B200 Qwen3.8-27B job, then the local fallback)
- vLLM: `/health` 200, `/v1/models` 401 without the key and 200 with it; the self-test passed with the key.
- Router: 401 without the key. OpenCode, which sends it, fixed the bug-fix task on the cluster, then on the local model after the job was stopped.
- llama-server: 401 without the key, `/health` 200. `ps` shows `--api-key-file`, never the key.
- Servers started before v0.2.0 have no key and still work; the router sends none to them.
