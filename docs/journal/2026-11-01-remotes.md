# Remotes: any machine as a model server

**Status:** OPEN. Proposal under discussion; to be built on a branch and tested before `main`.

## Question
How can oca use a DGX Spark, or any other machine, beside UCloud, switch between them transparently, and stay as easy to set up as `oca cluster up`?

## Proposal (2026-11-01)
- `oca remote add | up | down | status`. It replaces `oca cluster`, which stays as an alias. There are three kinds of remote:
  - `ssh`: oca installs itself on the machine over SSH, runs its local-mode server there, and connects through an SSH tunnel with a key. The installer already picks llama.cpp's CUDA build for ARM (untested on a Spark).
  - `ucloud`: as today.
  - `url`: an OpenAI-compatible server run by someone else.
- `oca/auto` uses the first live server in a set order, by default largest first: UCloud, then the Spark, then local.
- OpenCode gets the smallest context window in that chain, so a session survives a move.
- The first run asks about the local model, UCloud and SSH machines.

Steps, on branch `remotes`:
1. `oca remote` with ucloud and url kinds, and a router for any number of servers.
2. The ssh kind.
3. The first-run questions.
4. The Spark itself.

Steps 1 to 3 can be tested from a laptop, using this workstation as the ssh remote.

## Open questions
- Will several people share one server on the Spark? If so, the listing needs a folder they can all read.
- Is the Spark's GPU used for other work (then stop when idle), or is it dedicated?
- Besides automatic switching, should a session be able to pick a server by hand in OpenCode?
