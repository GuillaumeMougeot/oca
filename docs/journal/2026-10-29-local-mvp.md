# Local MVP (phase 1)

**Status:** RESOLVED. `oca` runs OpenCode on a CPU-only local model, end to end.

## Hypothesis (written before measuring)
- A dense 27B model on CPU is too slow, because generation is memory-bandwidth-bound.
- A 3B-active MoE (Qwen3.6-35B-A3B Q4) should give 20 to 30 tok/s generation and 100 to 300 tok/s prefill.

## Result
`llama-bench`, CPU only (`CUDA_VISIBLE_DEVICES=`). The host load average was about 6.7 because the machine is shared.

| Threads | Prefill (pp512) | Generation (tg64) |
|---|---|---|
| 8 | 87 | 12.6 |
| 16 | 141 | 12.1 |
| 24 | 136 | 11.4 |

- Generation came in at about half the prediction. Prefill was in range.
- Set `threads = 16` on this host: best prefill, and generation is flat across thread counts.
- Task: fix `add()` returning `a - b`, then run pytest, via `oca run -- run "..."`. Took 3m21s cold and 1m25s with a warm prompt cache. The fix was correct.

## Incident
- On the first run the model couldn't find pytest and ran `pip3 install --break-system-packages pytest`. OpenCode allows every tool by default.
- That put four packages into `~/.local/lib/python3.12`. They were removed.
- Fix: `agent.PERMISSION`.
  - Shell commands default to `ask`.
  - Read-only and test commands are `allow`.
  - `sudo` and `--break-system-packages` are `deny`.
- Verified: in non-interactive mode, the deny rule blocks and `ask` auto-rejects.

## Decisions
- Install: `install.sh` runs `oca setup` (binaries). The first `oca` repairs anything missing and asks before the 22 GB model download.
- On a machine with an NVIDIA GPU, oca downloads the CUDA build. `device=cpu` hides the GPU with `CUDA_VISIBLE_DEVICES=`, so one binary serves both modes. The CUDA runtime libs sit in a sibling directory and are added to `LD_LIBRARY_PATH`.
- OpenCode's config schema marks `provider`, `autoupdate` and `enabled_providers` as deprecated in favour of v2 keys (`providers`, `update`, `policies`). v1.19.5 still accepts them; the v2 keys are undocumented. Migrate when the docs catch up.
